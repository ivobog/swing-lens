## REL-MD-002 — retry and durable work — CLOSED

The old job classifier treated the Winner `ValueError` as `UNCLASSIFIED_RETRYABLE`; three outer retries, each with a new PARTIAL fetch run, re-requested all 198 already-successful items. The corrected classifier marks deterministic application/authority ValueErrors nonretryable. Historical-provider text is classified at the item boundary; timeouts, transient connection and pacing remain bounded retryable categories. Generic item exceptions no longer retry unless they are timeouts or connections. Frozen scope/contract mismatches have typed, nonretryable item reasons. Provider request IDs and item classifications are retained in metadata.

A fetch run is now bound to admitted scope/refresh/plan before item commits and is selectable in RUNNING/PARTIAL/FAILED states for the same exact identities. Restarting it reuses SUCCESS/SKIPPED checkpoints, preserves permanent FAILED rows, and retries only FAILED rows explicitly marked retryable. Counters are corrected when a failed row is reattempted. The job's same-plan manifest fingerprints the exact successful and failed feed-item sets; if a retryable outer error recurs with an identical set and no new success, `ACQUISITION_NO_PROGRESS_RETRY_GUARD` stops another same-plan attempt. The terminal parent reason includes affected ticker/feed/classification. A legitimate replan requires a new acquisition identity, predecessor and typed reason; a transient retry keeps the original scope/refresh/plan.

This changes a deterministic known-provider failure from three 90/180-second item backoffs per feed on four full passes to one terminal item attempt and no repeated success fetches. It does not assert that the whole pipeline must fail for a single unavailable ticker. A mixed transient/permanent set remains item-typed, with permanent rows visible; it is not collapsed to a generic retryable stage. Real-PG attacks prove (1) 198 SUCCESS plus six deterministic FAILED rows within an exact 204-item plan cause zero provider replay, (2) a timeout/invalid-contract/plan-mismatch set retries only the timeout, (3) success A is fetched once while transient B is retried, and (4) the no-progress job guard stops repeated same-plan failure sets. No second progress framework or migration was introduced.

The focused CLBK/OKE-style permanent-error test completed two cases in 1.14 seconds of pytest execution under concurrent gate load; each made one provider call and zero retry backoffs. This is a deterministic-path test measurement, not a claim of a new 100-symbol live-pipeline duration. Successful request paths retain the existing pacing and checkpoint behavior, as covered by the focused and full repository tests.
